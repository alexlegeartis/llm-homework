## Предсказание

В терминале с активным окружением:

```bash
export LLM_BASE_URL="http://127.0.0.1:8089/v1"
export LLM_MODEL="Qwen/Qwen3.5-4B"
export LLM_API_KEY="local"
export SUBMISSION_ID="kravatskiy-hw1"
python predict.py --index index --questions dev_questions.jsonl --output answers.jsonl --trace trace.jsonl --config config.json
```

Каждый запрос передаёт `X-Question-ID` и `X-Submission-ID`. Скрипт не читает эталоны и не переносит диалог между вопросами. Варианты обозначаются A–F по текущему порядку, затем переводятся обратно в фактические ID. Пути CLI могут быть абсолютными; запуск возможен из другой папки.

Выход — один JSON на вопрос: `id,answer_ids,abstain,rationale,citations`. В trace записываются фактические токены API, вызовы, время, поисковые запросы, найденные и отправленные блоки. Техническая ошибка отмечается отдельно и получает ноль при оценке.

## Архитектура

1. PyMuPDF извлекает символы, шрифты и координаты. Дроби, индексы, корни и надчёркивания переводятся в текст: `(a)/(b)`, `^{...}`, `root(n,...)`, `bar(...)`. Абзацы объединяются в пределах страницы: цель 850, максимум 1500 символов. Оригинальные ID сохраняются.
2. BM25 использует русские основы слов и математические обозначения, включая однобуквенные переменные. Формулы вопроса и вариантов нормализуются для поиска; в LLM передаётся исходный текст вопросов с LaTeX. Небольшой словарь математических понятий расширяет поиск; он не содержит готовых ответов, численных решений или ID вопросов.
3. Сначала берутся находки по расширенным запросам, затем — лучшие по исходному вопросу и вариантам: всего до четырёх основных фрагментов. К ним добавляются до двух ближайших продолжений; новая теорема, определение или доказательство останавливают расширение. Если блок ссылается на пронумерованную формулу, добавляется блок с её первым появлением. Оглавление исключено из итогового поиска. Каждый найденный фрагмент помещается рядом со своим продолжением; целые блоки упаковываются в бюджет 2200 входных токенов с резервом шаблона.
4. **Один вызов Qwen** в штатном режиме thinking: краткое обоснование (промпт просит одно предложение или формулу до 300 символов, схема ограничивает длину 350 символами при допустимых по заданию 1200), все верные варианты, отказ и до четырёх подтверждающих ссылок. Код переводит метки в исходные ID и добавляет ID вопроса. Наружу возвращаются ровно пять требуемых полей; код проверяет длину, уникальность и правила отказа. Повторяющиеся ID удаляются; при отказе оба списка очищаются с сохранением причины и расхода API. Отдельные предложения, обсуждающие только невыбранные варианты, удаляются; исходный текст сохраняется в trace как `rationale_before_filter`. Эта обработка одинакова во всех конфигурациях. Дополнительных проверок моделью, rewrite, reranker и адаптивного цикла нет.

Отказ означает недостаточность исходных сведений. Пропуск нужной теоремы поиском остаётся ошибкой. Параметры генерации одинаковы во всех экспериментах: temperature=1.0, top_p=0.95, top_k=20, min_p=0, presence_penalty=1.5, seed=42, max_tokens=4096, thinking включён с лимитом 3072 токена (`thinking_budget_tokens`), чтобы оставить место для итогового ответа. Endpoint должен поддерживать параметры из runtime; локальный llama.cpp их поддерживает. Расход `completion_tokens` включает рассуждения и итоговый JSON; сами внутренние рассуждения в ответ не выводятся. Все вызовы и фактический расход учитываются, лимиты проверяются до отправки запроса и по ответу API.

## Оценка и эксперименты

```bash
python evaluate.py --questions dev_questions.jsonl --gold dev_gold.jsonl --answers dev_answers.jsonl --trace dev_trace.jsonl --corpus homework_01_rag/data/corpus.jsonl
python run_experiments.py --index index --questions dev_questions.jsonl --gold dev_gold.jsonl --config config.json --output-dir .
python -m unittest discover -s tests -v
```

Пять конфигураций на одних и тех же 15 вопросах: без контекста; BM25 baseline с одним поиском и вызовом; итоговая система; без расширения запросов; без расширения контекста соседями и ссылками на формулы. Baseline использует три фрагмента по исходному вопросу и вариантам. У всех конфигураций одинаковы модель, sampling и исходный LaTeX вопросов. Baseline, итоговая система и обе её абляции используют один промпт и одну схему ответа. Способ подсчёта входного бюджета одинаков.

Результаты — [experiments.csv](experiments.csv), ответы и trace — `experiments/`. Можно выбрать прогоны через `--names final without_expansion`; `--summarize-only` пересчитывает метрики из готовых файлов без LLM. Восемь авторских вопросов находятся в `own_questions.jsonl` и `own_gold.jsonl`, по два на категорию.

Проверенный прогон Colab T4: **15/15 точных наборов вариантов**, Q=0.9811, локальная оценка **97.21/100** относительно собственного baseline. Все 75 ответов пяти конфигураций имеют проверенный расход API; пройдены 14 тестов. Подробности и ограничения — в отчёте.

`config.json`, `dev_answers.jsonl` и `dev_trace.jsonl` в папке задания соответствуют строке `final`. Измерения, выводы абляций и разбор ошибок — в [отчёте](report.md). Официальный baseline и его `C_ref` не предоставлены: локальная эффективность считается относительно измеренного BM25-baseline и не является официальной оценкой. Содержательная проверка обоснований остаётся отдельным требованием.

## Ресурсы и внешние инструменты

Для локальной Qwen предусмотрено 8 ГиБ RAM и около 10 ГБ диска; подробные измерения — в отчёте, `index/build_metrics.json` и `run_metadata.json`. Поиск выполняется на CPU, LLM работает отдельно. Версии всех зависимостей, включая транзитивные, закреплены в `requirements.txt`.

Использованы PyMuPDF, Hugging Face Tokenizers, Snowball, psutil и llama.cpp. При разработке, проверках и подготовке отчёта использовался Codex. Ответы экспериментов сгенерированы только заданной [Qwen3.5-4B](https://huggingface.co/Qwen/Qwen3.5-4B), GGUF — [Unsloth](https://huggingface.co/unsloth/Qwen3.5-4B-GGUF). Обучения, генеративного дополнения корпуса и вызовов LLM при сборке индекса нет.
